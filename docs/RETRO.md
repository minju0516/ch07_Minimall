# RETRO — 회고
## 잘된 점

- M2에서 코드를 쓰기 전에 판단 표를 두 차례 되돌려 고치고, 최종 표를 김윤영과 함께 확인해 승인했다. 이후 규칙을 한 개씩 구현하며 `git diff`로 승인한 표와 코드의 하한·창 길이·임계값·심각도를 대조했다. M4에서도 지표별로 표와 구현을 확인해 최종 공개 릴리스 R1~R5 모두 통과했다.
- 로그 분석은 AI의 요약만으로 확정하지 않았다. M5에서 Copilot이 제시한 INC 가설을 Claude가 번들 파일과 대조했고, 사람은 근거 로그 6줄을 원본 `logs.jsonl`에서 직접 열어 존재·내용·시각 순서를 확인했다. INC-2의 실제 사용자 영향 시작도 데이터 변경 시각이 아니라 지표 하락이 시작된 04:15로 바로잡았다.
- 수치에는 막으려는 실수와 허용할 차이를 함께 따졌다. 예를 들어 M5 OPS-CI 기준은 위험한 오답 하나를 통과시키지 않도록 하되, 작은 부분 감점 때문에 정상 작업까지 막지 않도록 영역별 점수 간격에서 계산했다. 그 결과 AI 산출물은 17.12/40점에서 우리 산출물은 38.66/40점으로 개선됐고, 런북 완결성도 0%에서 100%가 됐다.
- 계약서에 없는 기준을 그대로 추정하지 않은 점도 좋았다. M3에서는 PSI 0.25 기준만으로 결론 내리지 않고 문제지 그림 6의 PSI 0.1·유효한 이틀 연속 조건을 확인해 OPS_DESIGN에 먼저 정리한 뒤 구현에 반영했다.
- AGENTS.md 규칙이 실제로 작동했다. 마무리 단계에서 Copilot은 회고 초안을 쓰기 전에 팀 규칙 1에 따라 판단 표를 먼저 보여 주고 "두 사람이 승인했는지"를 확인했다.

## 아쉬운 점(특히 AI 를 믿었다가 틀린 순간)

- M4 요청에 결제 표본 하한의 단위를 적지 않자 Copilot은 알림의 분당 20건을 단계 누적 하한으로 가져왔다. 새벽 5% 카나리에서 충족할 수 없는 조건이 될 수 있어 사람이 발견해 단계 누적으로 고쳤다. 구현 후에야 승인 표의 20분과 다른 15분 면제 시간, 추천 입력 이상 시 전체 보류, 승격 전 baseline 정상 조건 누락도 확인했다. 특히 baseline 조건 누락은 `grep`으로 찾아 수정했다.
- M5 INC-2 분석에서 Copilot은 사용자 영향 시각 대신 데이터 변경 시각 02:03을 최초 이상 시각으로 제시했다. INC-3에서도 Copilot이 낸 가설 중 일부는 배포 로그와 다른 서비스 경고를 근거로 삼아, 실제 원인 증거인지 따로 걸러야 했다. 사람은 로그 ID를 원본 파일에서 열어 확인하고, 미끼 로그를 원인 근거로 채택하지 않았다.
- M2·M3·M5 문서 초안에서 Copilot은 사람이 직접 확인하지 않은 내용까지 “사람이 확인했다”고 적었다. M2에서는 확인할 수 없는 ticket 발행 여부도 기록했고, M3에서는 사람이 바꾼 내용과 직접 실행 여부를 잘못 적었으며, M5에서는 Claude가 대조한 로그까지 사람이 직접 확인했다고 썼다. 매번 기록과 실제 확인 범위를 사람이 대조해 고쳤다.
- M5 런북 초안은 INC-1의 설정 변경을 일반 조치처럼 두고, 추천 런북에는 INC-2의 특정 모델 버전을 고정했다. 한 장애 사례에 맞춘 절차는 다른 원인에서 잘못된 조치로 이어질 수 있어, 사례는 예시로 남기고 절차를 일반화했다.
- Claude도 틀렸다. M3 첫 판단 표 초안은 계약서의 "0.25 이상 큰 변화"를 그대로 기준으로 잡아 문제지 그림 6(PSI ≥ 0.1, 유효한 이틀 연속)과 달랐고, M5 ops-ci 기준값 첫 제안(파이프라인 100 · 알림 80 · 정책 90%)은 영역마다 엄격함의 기준이 제각각이었다. 두 경우 모두 사람이 문제지 그림과 점수 계산으로 확인해 고쳤다. AI가 둘이어도 서로를 검증해 주지는 않으므로, 기준의 출처는 사람이 원문에서 확인해야 한다.

## 다음 프로젝트에서 바꿀 것 3가지

1. 요청과 판단 표의 모든 하한·임계값에 단위와 집계 범위를 적는다. 특히 분당 값과 단계 누적값, 지표별 분모를 구분하고, 계약서 밖 기준은 구현 전에 설계 문서에 근거와 함께 정리한다.
2. 승인된 판단 표를 구현 완료 기준으로 삼는다. 각 변경 뒤 `grep`·`diff`로 조건·경계·예외·보류 시간을 표와 대조하고, 표본 하한이나 이력 요건이 실제 장애 구간에서 충족되는지도 확인한다.
3. AI의 로그 분석과 문서 작성은 검증 범위를 분리해 기록한다. 로그 ID와 원인 연결은 사람이 원본을 열어 확인하고, Copilot의 초안·Claude의 대조 의견·사람이 직접 확인한 사실을 구분한다. 런북은 개별 장애 사례를 절차에 고정하지 않고 일반화한다.

## AGENTS.md 에 실제로 추가 · 수정한 규칙

- 팀 규칙 4: 3분짜리 일시 급증보다 짧은 page 규칙을 만들지 않는다. (M2, 3분 급증과 구분되지 않는 짧은 page 규칙을 표 단계에서 제거)
- 팀 규칙 5: 결제·추천처럼 분모가 다른 지표는 자기 분모로 표본 하한을 정하고, 표본 부족은 보류하거나 창을 늘린다. (M2, `paymentAttempts`·`recImpr` 분모 및 하한 설계)
- 팀 규칙 6: `sim/`과 `scripts/eval.js`를 읽거나 가져오지 않고, 시뮬레이션 난수는 직접 구현한다. (M4, 검증 중 `sim/rng.js`를 읽고 사용한 사실을 기록한 뒤 금지 범위를 명시)
- 팀 규칙 7: 하한·임계 수치에는 분당·단계 누적·최근 N분 등 단위를 쓴다. (M4, 분당 20건이 단계 누적 하한으로 잘못 들어간 문제)
- 팀 규칙 8: 구현 후 승인한 판단 표와 코드를 `grep`·`diff`로 대조한다. (M4, 승인표에 있던 baseline 정상 조건이 코드에서 빠진 것을 `grep`으로 발견)
- 팀 규칙 9: 기준이 계약서가 아닌 문제지 그림·힌트에만 있으면 OPS_DESIGN에 먼저 정리한 뒤 에이전트가 따르게 한다. (M3, 그림 6의 PSI 0.1·유효한 이틀 연속 조건)
- 팀 규칙 10: 런북·규칙을 단일 장애 사례에 고정하지 않고 절차를 일반화한다. (M5, RB-ERR-01의 설정 복구 고정과 RB-REC-01의 INC-2 모델 버전 고정 수정)
- 팀 규칙 11: 에이전트는 AI_USAGE_LOG를 직접 수정하지 않으며, 사람 확인 범위는 실제 확인한 내용만 기록한다. (M2·M3·M5, 확인되지 않은 ticket·로그를 사람이 확인했다고 쓴 기록 수정)
