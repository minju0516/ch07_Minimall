## 2. 기준선 (AI 산출물, `npm run eval:ai`)
| 영역 | 공개 점수(%) | 가장 눈에 띄는 실패 |
|---|---|---|
| 파이프라인 게이트 | 41% | 테스트 40% 건너뜀(c03) · 키 하드코딩(c04) · 성능 하락 모델(c06) · 런타임 치명 취약점(c07) · 되돌릴 수 없는 컬럼 삭제(c10)를 통과시킴 |
| 알림 규칙 | 71% | 3분짜리 일시 오류 급증에 불필요한 호출(A3), 서서히 느려지는 지연을 42분 만에 감지(A5, 기준 25분) |
| MLOps 정책 | 19% | 안정 구간에서 41일간 불필요 경보(D1), 가격 null→0 데이터 오류 미감지(D3), 노이즈·평가 데이터 부족·누수·신규 사용자 하락·응답 시간 초과·결측 데이터인데 모델을 승격함(P3~P8) |
| 점진 배포 | 41% | 느려진 신버전을 100% 배포(R3), 우연한 오류(R4)와 외부 장애(R5)에 정상 릴리스를 롤백 |
| 런북 완결성(`npm run runbook -- --dir ai_ops`) | 0% (0/3) | 알림 규칙 3개 모두 runbook 필드가 없음 |

자동 평가 합계(공개 시나리오): 17.12 / 40점

팀장의 말 "AI 가 만든 운영 자동화가 공개 시나리오를 대부분 통과하니 그대로 써도 되겠다"에 대한 우리 팀의 한 문장 답: 공개 점수는 연습용 시나리오에서 규칙이 동작한다는 것만 보여 줄 뿐 숨은 시나리오(다른 시각·크기·조합)와 실제 운영을 보장하지 않고, 실제로 AI 산출물은 영역별 19~71%에 그쳐 위험한 변경과 나쁜 모델을 통과시키고 정상 릴리스를 막았으므로 그대로 출시할 수 없다.

## 3. 미션별 작업 단위와 확인 방법
| 미션 | 작업 단위 | 어떻게 확인하나 |
|---|---|---|
| M1 | 계약서 4장 규칙을 하나씩 판단 표(입력→판정→이유)로 만들고 승인 후 구현: 테스트 실패 · 건너뜀 비율 · 비밀 값 · 치명 취약점(개발 전용 제외) · 되돌릴 수 없는 마이그레이션 · 문서만 변경(통과) · 모델 변경은 M3 연결 | `npm run eval:pipeline`의 ✘·△ 설명, OPS_DESIGN 1절 |
| M2 | 오류율 급등과 3분 일시 급증 구분(지속 시간 반영), 평소 대비 상대 비교, 지연 증가 감지, 규칙마다 runbook ID 연결 | `npm run eval:alerts`, `npm run runbook` |
| M3 | 드리프트 감지와 데이터 품질 이상 구분, 재학습 조건, 승격 판단(신뢰구간 · 평가 크기 · 누수 · 구간별 · 응답 시간 · 결측), 이전 버전 보존 | `npm run eval:policy`, `npm run retrain -- --scenario shift`, OPS_DESIGN 4절 |
| M4 | 카나리를 기존 버전과 비교해 승격 · 보류 · 롤백 판단(외부 장애 오탐 방지, 지연 회귀 감지), 롤백 조건 | `npm run eval:rollout`, OPS_DESIGN 3절 |
| M5 | INC-1~3을 AI로 분석하고 인용한 로그 ID를 사람이 직접 열어 검증(미끼 로그 제외), 런북 완성, `scripts/ops-ci.js` 완성 | `docs/incident_findings.json`, `npm run incidents`, `npm run runbook`, `npm run ops-ci`(우리 산출물 통과 + `-- --dir ai_ops` 실패) |

## 4. 예상 위험과 안전장치 3가지
1. **점수 맞추기 위험** — 평가기나 시뮬레이터를 읽고 점수에 맞춰 숫자를 고르거나 시나리오 ID를 박아 숨은 시나리오에서 무너질 수 있다. → 임계값은 계약서와 SLO에서만 가져오고 값마다 근거 주석을 단다. `sim/ lib/ src/ scripts/`(ops-ci 제외) 등은 수정 금지이고, 제출 전 `git status`로 수정 금지 폴더에 변경이 없는지 확인한다.
2. **한쪽만 잘하는 위험(오탐/미탐)** — 알림을 둔하게 하면 장애를 놓치고 민감하게 하면 밤새 오탐이 나며, 게이트를 너무 막으면 정상 배포가 막힌다(점수는 탐지율과 정상 통과율의 기하평균). → 변경마다 ✘·△ 항목에서 무엇이 달라졌는지 기록하고 정상 시나리오가 깨지지 않았는지 함께 본다.
3. **AI 분석 · 판단을 그대로 믿는 위험** — Copilot이 그럴듯하지만 틀린 원인이나 미끼 로그를 근거로 말할 수 있다. → 코드 전에 판단 표를 받고 두 사람이 계약서와 대조해 승인한 뒤 작성하며, 로그 근거 ID는 파일을 열어 직접 확인한다. 같은 시도가 3번 실패하면 멈추고 원인 가설과 새 계획을 세운다. 비밀 값·개인정보는 코드·로그·문서에 쓰지 않고, 알림에는 런북, 배포에는 롤백 조건, 모델 승격에는 이전 버전을 붙인다.
