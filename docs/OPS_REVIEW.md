# OPS_REVIEW — AI 가 만든 운영 산출물 리뷰 (Mission 0·5)

## 1. 점검표 (8항목) — `ai_ops/` 4개 파일을 읽으며 해당 사례를 찾는다
| # | 점검 항목 | 의심 사례(파일 · 위치) |
|---|---|---|
| O1 | 고정 임계값 하나로 판단하는가(평소 대비 · 지속성 없음) | |
| O2 | 한 분(한 번)의 값으로 호출하는가(일시 급증에 취약) | |
| O3 | 전체 평균만 보는가(구간 · 비즈니스 지표 · 결제 실패 · 추천 품질 누락) | |
| O4 | 게이트가 "테스트 통과"만 보는가(건너뜀 · 커버리지 · 비밀 · 취약점 · 모델 품질 누락) | `ai_ops/pipeline.config.js` 5~7줄: 게이트가 tests-pass(실패 0) · build-ok 두 개뿐이고 deploy 단계 게이트는 비어 있음. 건너뜀 · 커버리지 · 변이 점수 · 비밀 값 · 취약점 · 마이그레이션 · 모델 · 스모크 검사가 없음 |
| O5 | 카나리를 기존 버전과 비교하지 않고 절대값으로만 보는가(외부 장애 오탐 · 작은 회귀 미탐) | |
| O6 | 재학습을 달력으로 하거나 평균 변화만 보는가(데이터 품질과 드리프트를 구분 못함) | `ai_ops/policy.js` 12줄: 14일마다 무조건 재학습. 4~8줄: 오늘 하루 카테고리 평균 위치 변화 3% 초과만 보고 데이터 품질 · 표본 수 · 주말 · 가격 분포를 보지 않음 |
| O7 | 모델 승격을 "점수가 올랐나"로만 판단하는가(신뢰구간 · 구간별 · 평가 크기 · 누수 무시) | `ai_ops/policy.js` 16~18줄: 후보 적중률이 챔피언보다 높기만 하면 승격. 신뢰구간 · 평가 크기 · 누수 · 학습 데이터 결측 · 구간별 하락 · 지연을 보지 않음 |
| O8 | 알림에 런북 · 담당 · 복구 확인이 없는가 | `ai_ops/alerts.js` 4~25줄: 규칙 3개 모두 runbook 필드가 없음(`npm run runbook -- --dir ai_ops` 0/3). 담당 · 처음 5분 · 에스컬레이션 · 복구 확인이 없음 |

## 2. 결함 표

|---|---|---|---|---|---|
| D-PIPE-1 | `ai_ops/pipeline.config.js` 5~7줄 | O4 | 테스트 실패만 막아서, 테스트를 건너뛰거나 위험한 내용을 넣어도 실패가 0이면 그대로 배포된다 | c03 테스트 40% 건너뜀, c04 PG 키 하드코딩, c06 성능 하락 모델, c07 런타임 치명 취약점, c10 되돌릴 수 없는 컬럼 삭제를 모두 통과(파이프라인 41%) | validate → test → model-eval → build → staging 5단계에 게이트 13개를 계약서 4.2대로 구현. 모델 변경은 `shouldPromote` 재사용(OPS_DESIGN 1절) |
| D-POL-1 | `ai_ops/policy.js` 4~8 · 12줄 | O6 | 달력 재학습과 하루치 평균 위치 변화만으로 판단해, 주말 계절성을 드리프트로 보고 데이터 고장은 놓치며, 망가진 데이터로도 재학습한다 | D1 안정 구간(주말 포함)에서 불필요 경보, D3 상류 ETL 고장(가격 null→0)을 감지 못하고 재학습 | 표본 부족 → 데이터 품질 → 분포 변화 순서로 판정, PSI ≥ 0.1이 유효한 이틀 연속, 주말 제외, 품질 문제면 fix_data, 7일 쿨다운(OPS_DESIGN 4.1~4.3) |
| D-POL-2 | `ai_ops/policy.js` 16~18줄 | O7 | 점수가 조금만 올라도 승격해, 노이즈 · 작은 평가 · 누수 · 나쁜 학습 데이터 · 일부 사용자 하락 · 느린 모델이 운영에 올라간다 | P3 노이즈 범위, P4 평가 데이터 부족, P5 평가 · 학습 겹침, P6 신규 사용자 하락, P7 응답 시간 초과, P8 결측 많은 학습 데이터를 모두 승격 | 계약서 5.3의 6개 규칙을 순서대로 검사하고 입력이 없으면 거절(OPS_DESIGN 4.4) |
| D-RB-1 | `ai_ops/alerts.js` 4~25줄 | O8 | 새벽에 page를 받아도 무엇을 먼저 보고, 무엇을 하고, 언제 누구를 부르고, 언제 복구로 볼지 알 수 없다 | 모든 page 상황. 예: INC-3 결제 장애에서 배포 롤백으로 잘못 대응할 수 있음(외부 장애는 우회가 필요) | 알림 규칙 8개마다 런북 연결, 처음 5분 · 완화 조치 · 에스컬레이션 · slo.json 수치로 된 복구 확인 작성. INC-1~3 결론을 반영(런북 100%) |
