## 3. 우리 산출물이 숨은 시나리오에서 틀릴 수 있는 곳 (한계 3가지)
1. **결측이 없는 데이터 고장은 승격 게이트를 통과한다.** `shouldPromote`의 `BAD_TRAIN_DATA`는 학습 데이터 결측률만 본다. INC-2처럼 결측률은 0.00인데 가격 0 비율이 0.31인 데이터로 학습한 모델은 승격 단계에서 막히지 않고, `detectDrift`의 0원 비율 검사(`priceBins[0] ≥ 0.20`)가 먼저 잡아야만 막힌다(POSTMORTEM 재발 방지 조치).
2. **주말 제외와 직전 유효일 탐색이 만드는 빈틈.** 주말을 감지에서 빼서 월요일에 드리프트가 확정되면 재학습 기준 분포가 토 · 일 · 월 3일 평균이 되어 주말 쪽으로 치우칠 수 있고, 직전 유효일 탐색에 기간 제한이 없어 긴 연휴 뒤에는 오래전 날과 "이틀 연속"으로 묶일 수 있다. 공개 시나리오(D2)에서는 재학습이 1회로 나타나지 않았다.
3. **공개 사례로 검증하지 못한 게이트 판단.** 문서 외 변경인데 빌드 결과가 없으면 차단, 커버리지 값이 없으면 통과로 정했지만(OPS_DESIGN 1절) 공개 변경 10건에 해당 사례가 없어 검증하지 못했다. 문서와 코드가 섞인 변경도 공개 사례가 없다.
4. **새벽 시간대 결제 알림의 미탐.** 결제 실패 규칙(RB-PAY-01)은 분당 시도 20건 미만인 분을 초과로 세지 않는다. INC-2 지표 기준 새벽 300분 중 121분이 20건 미만이라 새벽에는 결제 장애를 놓칠 수 있다(OPS_DESIGN 2절).
5. **새벽 5% 카나리 단계에서 결제 · 추천 검사가 제외된다.** 표본이 모자라 20분 뒤 해당 조건을 제외하므로, 결제만 망가진 릴리스가 5%를 통과할 수 있다. 모형(1,000회)에서 새벽 5% 결제 실패율 30% 릴리스는 998회 통과했고, 이후 25% 이상 단계에서 잡히는 정도는 확인하지 못했다(OPS_DESIGN 3절 한계 1).

## 4. 사람이 끝까지 책임져야 하는 판단
- 계약서에 없는 기준을 어디서 가져올지: PSI 0.1 · 이틀 연속은 문제지 그림 6에만 있었고, 주말 처리와 쿨다운 경계(7일째)는 어디에도 없어 사람이 정하고 OPS_DESIGN에 근거를 남겼다.
- 장애의 원인과 최초 이상 시각의 최종 채택: AI는 데이터 변경 시각(02:03)을 최초 이상으로 잡고, 배포 로그 · 다른 서비스 경고를 근거로 삼았다. 근거 로그 ID는 사람이 파일을 직접 열어 확인한 뒤에만 채택했다.
- 게이트 기준값을 얼마나 엄격하게 할지: 어떤 실수를 반드시 막고 어떤 차이를 허용할지는 점수가 아니라 운영 위험의 판단이다(OPS_REPORT 2절).
- 외부 장애에서 롤백하지 않을 판단: 배포가 있었다는 사실만으로 롤백하면 정상 버전을 되돌린다(INC-3).
- 알림 임계값과 지속 조건을 어디까지 정당화할지: 1%, 4분 연속, 8분 중 5분 같은 값은 계약서에 없는 제안값이다. 지속 조건을 길게 하면 오탐은 줄지만 감지가 늦어지고(A5 31분), 짧게 하면 일시 이상에도 새벽에 사람을 깨운다. 어느 쪽 위험을 감수할지는 사람이 정해야 한다(OPS_DESIGN 2절).
- 롤백 이후 결제 정산 · DB 스키마 호환 확인은 현재 런북에 없고, 사람이 따로 확인해야 한다(OPS_DESIGN 3절 점검 질문 2).
